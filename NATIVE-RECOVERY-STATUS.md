# Native recovery development status

The native account screen can request a PKCE recovery email with the exact callback `cleanproof-demo://reset-password`. It stores the verifier in device-only SecureStore, consumes it before exchanging the one-use code, and uses an in-memory recovery session distinct from the encrypted company session. The callback route clears displayed route parameters, validates age and backend, sets a new password, signs out the recovery session and directs the user to the existing onboarding sign-in. The callback screen does not unlock company records. Email delivery is not confirmed by request acceptance.

This is an unverified development implementation, not a customer-release feature. Existing app.json scheme is `cleanproof-demo`; do not change application IDs or signing for existing installations. For a future authorised staging test, add the exact `cleanproof-demo://reset-password` entry under Supabase Authentication > URL Configuration > Redirect URLs. Keep the existing HTTPS Site URL and web callback; do not add a wildcard. No hosted setting was changed. Confirm mail templates use the generated confirmation URL and the callback opens the installed development app, without copying links or codes into logs. Custom URL schemes may be claimed by other apps; PKCE prevents exchanging a stolen code without the device-held verifier, but verified HTTPS app links should be considered for release.

Native customer-first entry parity, account switching, returning-company workspace selection and native secure recovery are not yet verified or complete. Some existing native workspace selection only supports owners; do not create new empty workspaces to conceal this. Physical Android and iOS builds, recovery, email delivery, expiry, two-account isolation, sync and browser acceptance are all pending. Typecheck, 124 host tests and five email-entry checks passed with one optional native test skipped; connected web export succeeded. These are not native device or real-service recovery evidence. The original browser's device-only work is unbacked up; do not deploy over connected staging until it is protected.
