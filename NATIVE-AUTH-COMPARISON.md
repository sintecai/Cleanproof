# Native customer authentication increment

The connected web customer entry uses CustomerEntry.web.tsx, a protected browser session store and PKCE link recovery. Native uses app/onboarding.tsx, AuthConnection and an encrypted SQLCipher session store backed by a device-bound SecureStore key. Both call the same email/password Auth service and immediate-signup policy; they do not share the same entry screen or workspace bootstrap. Native recovery previously requested a numeric code even though the customer email is link based, and its native reset route is a placeholder. Native automatic session restore was gated on hasCustomerSession(), which is false in the native implementation.

This increment attempts to restore a saved native session on opening the account screen and checks memberships before presenting it. On native the misleading recovery-code path is replaced with an honest notice directing the user to the connected web recovery flow; no email is requested by that button. The older web onboarding behaviour is retained. This is an interim safety change: native link recovery, customer-entry parity, correct account/company reopening and secure account switching still require implementation and real device acceptance. It does not claim those features work.

Typecheck, host tests, email-only checks and connected web export passed. Actual native registration, sign-in, restore, logout, password recovery and record reopening have not been run. This environment has no Android SDK/adb or Xcode/iOS simulator; no new native test binary was produced. The original browser's device-only records remain unbacked up; staging was not deployed or altered. Password recovery and callback delivery must be verified end-to-end without exposing tokens. See the Supabase native deep-linking documentation when implementing the native PKCE recovery flow.
